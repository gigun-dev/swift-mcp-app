## 0. 提出仕様(講義 PDF から確定・違反は減点)

| 項目 | 仕様 | 備考 |
| --- | --- | --- |
| 動画尺 | **最大 5分** | 超過分は**断りなく強制カット**+超過に応じ減点 |
| ファイルサイズ | **100MB 以下** | 超過は強制再エンコード(画質劣化)+減点 |
| ファイル名 | **学籍番号.mp4** | 例 `1241445678.mp4` |
| 形式 | mp4 / mpg / wmv / mov / avi | PowerPoint そのままは不可 |
| 冒頭 | **題目・学籍番号・氏名** | 動画の最初に |
| 構成 | **二部構成**(第一部=スライド紹介 / 第二部=デモ動画) | 「満たさない項目の件数に応じて減点」 |
| 第一部の必須項目 | ①概要・仕様 ②**開発プラットフォーム(iOS+Swift)** ③詳細な説明 ④工夫した点・苦労した点 | ②は当初の構成案から漏れていた。明示スライドを立てる |
| デモ | 原則実機。やむを得ない場合は**理由を動画内で明示**してエミュレータ可 | 担当教員に確認済み: **Simulator 可**(実機要件は Android 端末貸与の制約由来) |
| コード | **GitHub に push**(プロジェクト全体)。最後の push が締切超過しないこと | 提出リポジトリ = `gigun-dev/swift-mcp-app` |
| 評価観点 | アプリの実用性・完成度・難易度 / プレゼンの完成度 | 相互評価(受講生+教員+TA) |

### 二部構成についての判断(重要)

ユーザー意向は「厳密に2部構成でなくてよい・デモを機能詳細の中に入れてもよい」。
一方で講義仕様は二部構成を明記し、**満たさない項目は件数で減点**と書いている。

> **2026-07-31 改訂: 初版の「ハイブリッド構成」は撤回し、統合構成を採用。**
> ユーザーの再指摘を受けて PDF を読み直した結果、初版の前提が誤っていた。

**誤っていた前提**: 「二部構成を満たさないと件数で減点される」。
**実際**: 減点条項(p5)が例示するのは「サイズなど仕様を満たしていない場合」
「Powerpoint のまま提出など」= **すべて形式面(尺・サイズ・ファイル形式)**。
内容構成(p3)は「〜すること」とあるだけで、減点の明示的対象として例示されていない。
一方で評価は5段階総合であり、**「デモ動画におけるアプリとしての評価も忘れずに考慮すること」**
と明記されている。

→ **守るべき実質は「二部に割ること」ではなく、
「評価者が『アプリの実動作を見た』と認識できるまとまった実演があること」。**

#### 採用: 統合構成(前半=語り / 後半=実演しながら説明)

詳細説明(講義必須③)と工夫・苦労(同④)を、**独立スライドではなくデモ映像の上に
注釈オーバーレイとして載せる**。

**効果**:
- デモ実尺 110s → **145s(+32%)**。
- 説明が「動いている画面を見ながら」伝わるので理解度が上がる。
- スライドが 9枚 → 7枚に減り、制作コストも下がる(締切に効く)。

**形式リスクの潰し方**: **区切り札を1枚入れて「第二部 デモ」と明示する**。
形式を厳守する採点者にも二部構成として読める。ユーザー意向の「機能紹介とデモを
分割しない」は、説明がデモ映像の**上で続く**ことで満たされる。

**副作用と対策**: 「工夫・苦労」が注釈だけだと読み落とされる
→ デモ中のカード描画の瞬間に**大きめのテロップ**
(「ホスト SDK は TypeScript のみ / iOS ネイティブの汎用ホストは前例ほぼ無し」)を出す。

- ボツ案①(初版): 厳密な二部構成 + 詳細説明への短クリップ埋め込み
  → 5分では説明とデモが互いを削り合う。**減点条項の読み違いに基づく過剰な保守だった**。
- ボツ案②: 区切り札も置かず完全に融合
  → 「デモを見た」と認識されないリスクだけが残る。札1枚は 10秒で買える保険。

## 1. 題目(確定 2026-07-31)

> # MCPHost — ひとりのカレンダーを、みんなの道具へ
> 〜 AI エージェント × 自作 CalDAV サーバー 〜

アプリ名は `MCPHost`(bundle `dev.gigun.mcphost`)。
note の「世の中のカレンダーアプリはほとんど 1人用の道具です」に直結する、
思想を前面に出した題目。

### 採用時に指摘したリスクと、その吸収方法(重要)

**リスク**: 共有(calendarserver-sharing)と招待(RFC 6638)は**未実装**。
題目が「みんなの道具へ」を掲げる一方でデモは単一ユーザーなので、
放置すると「言ったことを見せていない」と読まれうる。

**吸収方法(確定)**: 題目を**ビジョンの宣言**として立て、**② Hook で先に予告し、
⑥ まとめで回収する**。乖離ではなく**物語の弧**にする。

> ② Hook: 「目指しているのは、ひとりのカレンダーを、みんなの道具にすること。
> ただ今日見せるのは、その第一歩です。」
>
> ⑥ まとめ: 「この先は、予定の共有と招待、それと端末を開かなくても届くリマインドを
> 考えています。ひとりのカレンダーを、みんなの道具へ。」

- **Hook で先に「今日見せるのは第一歩」と宣言してしまう**のが効く。
  後出しの言い訳ではなく、話の順序になる。
- **未実装を実装済みと誤読させない**(§3 ⑥ の言い切り規律と同じ方針)。
  「考えています」で未来形に留める。
- ボツ案: 題目をデモの内容に合わせて縮める
  → 思想(個人指向からの脱却・調整の摩擦)が題目から消えるため、ユーザー意向に反する。

## 2. 尺配分(確定 2026-07-31 **第2版**)

> **第1版からの改訂理由(ユーザーFB・重要)**
>
> **① 主役の取り違え。** これは**ネイティブアプリ開発の授業**であり、成果物は
> **swift-mcp-app(アプリ)**。caldav サーバー / MCP は「**アプリに必要だったので自作した派生物**」。
> 第1版は無意識にサーバーとその思想を主役に置いていた。
> 「ひとりのカレンダーを、みんなの道具へ」はあくまで**ネイティブアプリとしての**主旨。
> → デモも **MCPHost が主軸、iOS 純正カレンダー/リマインダーは「おまけ」**の比率にする。
>
> **② 思想に寄りすぎて抽象的。** 第1版は課題提起系が3枚(S2/S3/S4)を占め、
> ほぼ思想だけを語る構成だった。聴衆(同級生)は **MCP も CalDAV も知らない**。
> → 思想を**1枚に圧縮**し、空いた尺で **MCP とは / MCP Apps とは / アーキテクチャ**を足す。
> アーキテクチャは「分かる人向けに軽く」= **Cloudflare Workers + D1** を明示する程度。
>
> **③ MCP Apps の説明が必須。** デモの見せ場は「チャットの中にカードが出て、それを操作すると
> またツールが呼ばれる」こと。この前提知識が無いと**デモの凄さが伝わらない**。

> **第3版への再改訂(2026-07-31 夜・ユーザーとの箇条書きレベルの擦り合わせを経て)**
>
> **④ ストーリーを「hook → デモが機能ツアー」へ。** 具体例(TDR MCP + caldav MCP の
> チャットの流れ)を見せる過程で、実装した機能を順に見せていく。デモが全体の 53%。
>
> **⑤ MCP / MCP Apps の解説スライドを廃止。** 聴衆は web も MCP も詳しくない大学3年の同期で、
> かつ 5分では詳細を語る時間がない。**「ふわっとでいい」**というユーザー裁定に従い、
> ③ の1行(「AI が外部サービスを呼ぶ標準規格」)だけに縮退。**浮いた60秒をデモへ回した**。
>
> **⑥ アーキテクチャも専用スライドを廃止**し、③ 下部の1行ストリップへ。
> 「軽く、分かる人向けに少しだけ」に1枚使うのは過剰と判断した。
>
> **⑦ ツール許可を機能として前面に。** 「エージェントに操作させる不安があるはず」という
> ユーザーの指摘どおり、これは技術的苦労話ではなく**聴衆に効く価値提案**。
> ③ の特徴カードへ置き、デモでは**最初の1回だけポップアップを見せて以降は全部許可**(10秒)。
>
> **⑧ 課題リマインドは主軸から外した。** サーバー駆動通知は通知手段(LINE / アプリ通知)が
> 未決で、かつ依存度が最も低いレイヤー。**⑥ まとめの「見据えている将来機能」**に留める。
>
> **⑨ テーマを白基調へ。** ビジネスライクに。indigo `#4f46e5` 単色アクセント +
> amber は1スライド1箇所まで。Lucide アイコンは飾りではなく**項目の識別子**として使う。

> **第4版(2026-08-01)— 12枚構成 + デモ2本。「苦労した点」の対象を差し替え。**
>
> **⑩ 6枚 → 12枚 + プログレッシブ目次。** LT の実例を調べ直した結果、
> 「1枚あたりの情報量を減らして枚数で刻む」ほうが 5分の口頭発表には合うと判断した。
> 下部に **4セクションのナビ**(つくったもの / しくみ / 苦労したこと / これから)を
> 常設し、いま話の何合目かを常に見せる。
>
> **⑪ デモは1本にまとめない。** 「1本の連続デモ」を要求する規定は講義仕様に無い。
> **デモ①(4枚目「使ってみます」)** と **デモ②(9枚目「いちばん苦労したところ」)**の
> 2本に割り、それぞれ直前のスライドの主張の実演として置く。
>
> **⑫ 「苦労した点」を差し替えた(ユーザー裁定・本改訂の主眼)。**
> 第3版までは **「副作用のある操作を誰が確認するか(HITL)」** を苦労として立てていたが、
> **これは苦労ではない**。既存の MCP 実装に前例が揃っており、正解が最初から明確だった
> (実際、サーバー側で確認を強制する実装は「ホストの責務」と判明して破棄している
> — `caldav/docs/modeling/15` §1)。
>
> 実際に苦労したのは **MCP App(チャットの中に出る UI カード)のベストプラクティス探し**で、
> ここは**業界的にも正解が確立されていない**。論点は3つに割れる:
>
> | 論点 | 実際に起きたこと(一次記録) |
> | --- | --- |
> | **どこまで出すか** | タスクは増え続けるので inline カードに収まらない。カード内スクロールはホストごとに挙動が違ううえ、Anthropic / OpenAI 双方の UI ガイドラインが禁止している。→ プレビュー5件 + 全画面へ昇格(`caldav` `fold.ts` の `INLINE_PREVIEW_MAX=5`)。`modeling/15` §B |
> | **どこで入力するか** | inline ドラフト行 か 全画面フォームか で **3回向きを変えた**(07-17「畳み中だけ昇格」→ 07-22「常時全画面」→ 07-24「inline へ回帰」)。決着した理由は実機事実 — 表示モード遷移で WKWebView の document が作り直され、**遷移をまたいでフォーカスを運べない**。`modeling/15` §C-1/C-5 |
> | **いつの状態を映すか** | 過去の会話を開いたときカードをどう出すか。静的スナップショット(操作不能)→ 現在のサーバーへ live 再接続 へ変更。さらに「現在状態の確認が済むまで操作不可にする gate」を作って**撤去**(net -227行)、鮮度は SWR(60秒判定)へ委譲。完了タスクの残骸を5秒で退場させる/削除ゴーストを廃止する、も同じ筋。`swift-mcp-app/docs/log.md` 2026-07-23 の各節 |
>
> 共通の背景は **MCP Apps 仕様の「空白」**: 表示モード遷移時の iframe 状態や focus の保存、
> inline のサイズ追従は「ホストの裁量」と書かれているだけで規定が無い。
> だから**動かしてみるまで分からず、決めたことを自分で文書に残すしかなかった**。
> これはそのまま ④工夫した点・苦労した点 の実体になる。
>
> **⑬ 上記の統合で 13枚 → 12枚。** 旧「苦労した①(副作用の確認)」「苦労した②(カードの大きさ)」の
> 2枚を、9枚目「いちばん苦労したところ」1枚へ畳んだ(ユーザー指示: 1枚にまとめて分かりやすく)。
> **ページ番号は全スライド `n / 12` へ振り直し済み。**

### ▶ デモ①(0:57–1:57 / 60s)

> 映像に合わせて読む。**ビート間で黙ってよい** —— 詰めて読まない。

## 4. デモシナリオ(第二部)

### 画面構成(ユーザー意向: 縦長なので 2〜3画面を並列)

```
┌──────────┬──────────┬──────────┐
│ MCPHost  │ 純正      │ 純正      │
│ (チャット │ カレンダー │ リマインダー│
│  +カード) │          │          │
└──────────┴──────────┴──────────┘
   操作側        ← 何もしていないのに現れる →
```

3画面すべて **同じ caldav サーバー**を見ているので、
「MCPHost で依頼 → 純正アプリに勝手に現れる」が**1画面で同時に証明できる**。
これが本作の一番の見せ場(ハイライト)。

### シナリオ(所要目安 110s)

1. **(10s)** MCPHost を起動、コネクタ一覧を見せる(caldav / TDR Wait Times の2つ)。
   → 「汎用ホスト」であることの証明。OAuth 接続済みの状態から始める(認証フローは尺を食う)。
2. **(35s)** チャットで自然言語依頼。
   例: 「明日ディズニーに行く。混雑予想を見てアトラクションを回る予定を立てて。持ち物も TODO にして」
   → TDR MCP で混雑照会 → caldav へ予定作成 + TODO 作成。
   → **カードがチャット内にインライン描画される**ところを見せる。
3. **(20s)** カード内を操作(TODO をチェック / 予定の詳細を開く)。
   → 「カードは静止画ではなくツールを呼び戻す」ことの証明。
4. **(30s)** **ハイライト**: 右2画面に注目。**何も操作していない純正カレンダーと
   純正リマインダーに、予定と TODO が現れている**。
   → 「既存の習慣を壊さない」の一画面証明。
5. **(15s)** 逆方向: **純正リマインダー側でチェック** → MCPHost のカードに反映。
   → 双方向であることの証明。時間が足りなければここを削る(削り代)。

### 撮り方の判断

- **Simulator 収録で確定**(教員確認済み)。冒頭に「エミュレータ使用」の断りテロップを入れる
  (講義仕様の「理由を明示」に対応。理由は「複数画面の同時比較のため」で十分)。
- 3画面同時収録は **macOS 側の画面収録で Simulator 3台を並べて 1発撮り**が最も安全。
  編集での同期合成はズレ調整コストが高く、締切的にリスク。
- **削り代の優先順位**: 手順5 → 手順3 → 手順1 の順に削る。手順2・4 は死守。
- **リアルタイム性は不要**(事前収録)。よってツール呼びのレイテンシは編集でカットできる
  → V5(コールドスタート)の優先度を下げる。**ただし待ち時間が長いテイクは尺を食う**ので、
  撮影前に一度叩いて温めておくこと自体は続ける。

## 4.1 デモの主従(2026-07-31 改訂・**最重要**)

## 4.6 MCP 2026-07-28 仕様改訂への対応(裁定: **発表前は実装しない**)

一次資料: [仕様](https://modelcontextprotocol.io/specification/2026-07-28/) /
[changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) /
[MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/) /
[Claude blog](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude)

### 変更規模(主要な破壊的変更)

- `initialize` / `notifications/initialized` **ハンドシェイク廃止** + `Mcp-Session-Id` 廃止
  (プロトコルの完全ステートレス化)。版・クライアント能力は毎リクエストの `_meta` で運ぶ。
- **`server/discover` が MUST** — サーバーが実装必須の新 RPC。
- **全 result に `resultType` 必須**(`"complete"` / `"input_required"`)。
- HTTP GET エンドポイント + `resources/subscribe`/`unsubscribe` → `subscriptions/listen` に置換。
- `ping` / `logging/setLevel` / `notifications/roots/list_changed` 削除。
- MRTR(Multi Round-Trip Requests)がサーバー起点リクエスト(sampling/elicitation/roots)を置換。
- エラーコード renumber、list 系に `ttlMs` / `cacheScope` 必須、`Mcp-Method`/`Mcp-Name` ヘッダ必須。
- 認可: DCR(RFC 7591)を **非推奨**化し Client ID Metadata Documents へ。RFC 9207 `iss` 検証。

### 裁定と根拠

**発表前は実装しない。** 理由(優先度順):

1. **デモへの影響がゼロ** — デモは swift-mcp-app(自作クライアント)⇄ caldav(自作サーバー)の
   **閉ループ**。外部が版を強制しない。claude.ai は検証用でデモには登場しない。
2. **旧版は「壊れた」のではない** — 2025-11-25 は有効なリビジョンであり、版ネゴシエーションが
   ある以上、旧版サーバーはその版を話し続けるだけ。
3. **打ち切り日は未告知** — Claude 側は「Claude 製品へ順次展開」止まり。しかも今回
   **feature lifecycle policy(最低12ヶ月の非推奨ウィンドウ)が明文化された** = むしろ安心材料。
4. **締切前日に本番 deploy を伴う大改修は、デモを壊す唯一の現実的な経路**。

得られるはずだったメリット(「最新仕様に追従済み」と言えること)は、**語りで代替できる**(下記)。
ステートレス化自体は Workers と本質的に相性が良い(セッション廃止=エッジ/ラウンドロビン向き)が、
それは**急ぐ理由ではなく、丁寧にやる理由**。

### 今日やる予防措置(必須・5分)

- **デモまで `bun install` / SPM の依存再解決を走らせない。**
  `swift-mcp-app` は `swift-sdk from: "0.12.1"`、caldav は `@modelcontextprotocol/sdk ^1.29.0` と
  **どちらもレンジ指定**。lockfile は commit 済みなので現状は安全だが、再解決すると
  SDK が上がって挙動が変わりうる。

### 発表での扱い(むしろ加点材料)

S7(工夫・苦労)または S8(これから)に 1行入れる:

> 「MCP は3日前の 2026-07-28 に大きな仕様改訂があり、ステートレス化と、拡張の
> バージョン管理フレームワーク化が入りました。本アプリは 2025-11-25 版で実装しており、
> 公式の12ヶ月移行ウィンドウに沿って計画的に移行します。」

さらに **MCP Apps が正式に versioned extensions framework に載った**のは、
本プロジェクトが賭けた路線が標準化側に追認されたということ。
「工夫した点」の裏付けとして強い。

### 移行タスク(発表後・両リポジトリへ起票)

- **caldav**: 2026-07-28 移行スライス(ステートレス化 / `server/discover` / `resultType` /
  `subscriptions/listen` / ext-apps の extensions 宣言 / list 系の `ttlMs`・`cacheScope` /
  DCR → CIMD)。**ステートレス化は Workers と好相性なので本質的に歓迎すべき変更**。
- **swift-mcp-app**: swift-sdk が新版対応したら追随。`server/discover` を使った
  up-front 版選択と後方互換プローブを実装。
